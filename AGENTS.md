# AGENTS.md

Guidance for AI coding agents working in this repository.

## Project overview

[C]Worthy's fork of UCLA ROMS: a free-surface, terrain-following regional
ocean model in Fortran (fixed-form `.F` and free-form `.F90`), MPI parallel,
with MARBL biogeochemistry, aimed at marine carbon dioxide removal. There is
no central ROMS executable: each configuration compiles separately, because
CPP macros drive compile-time optimization. Runtime settings come from a
namelist passed as the first argument: `./roms namelist.nml`.

## Environment and build

```bash
export ROMS_ROOT=<repo root>
export PATH=$PATH:$ROMS_ROOT/Tools-Roms      # the mpc preprocessor lives here
cd $ROMS_ROOT/Tools-Roms && make             # once: partit, ncjoin, and others
cd Examples/Iceland/Iceland_parent && make   # per-case build, produces ./roms
mpirun -n <NP_XI*NP_ETA> ./roms namelist.nml # from &PARAM_SETTINGS
ncjoin roms_his.*.nc                         # join per-rank output
```

Builds fail without `mpc` on `PATH`. You also need `MPIHOME` and `NETCDFHOME`
(plus `NETCDFFHOME` if netcdf-fortran has its own prefix), `MARBL_ROOT` when
`MARBL` is defined, and `PIO_ROOT` and `PNETCDFHOME` when `PARALLEL_IO` is
defined.

- Conda (Linux, containers, small machines): create and activate the
  environment described in `docs/installation/dependencies.md`, then
  `source ci/set_environs.sh` from the repository root to set `MPIHOME` and
  `NETCDFHOME` from it. That script sets `ROMS_ROOT=.`, so export an absolute
  `ROMS_ROOT` again afterwards. Add Python packages with
  `mamba install -c conda-forge <pkg>` (or `conda install`), not pip, and ask
  the user first.
- HPC: `source environments/<machine>.sh` from inside `environments/`; the
  paths in those scripts are relative.
- Knobs, with defaults in `src/Makedefs.inc`: `COMPILER=gnu|intel` (`intel`
  means ifx), `BUILD_MODE=regular|debug|test|strict|vtune|grof`, and
  `MPI_WRAPPER=auto`. Use
  the same `COMPILER` for `Tools-Roms` and ROMS. After changing them, run
  `make compile_clean && make`.
- Never edit `src/` to set up a simulation. Per-case Makefiles rsync `src/`
  into a local `Compile/` and overlay the case's own `*.h`, `*.F`, `*.F90`,
  and `*.opt` files.
- `Makedefs.inc` greps the case's `cppdefs.opt` for `MARBL`, `NHMG`, and
  `PARALLEL_IO` to choose link dependencies, so the file must exist before
  `make`.
- `src/Make.depend` is tracked but derived. Never hand-edit it. When a change
  adds, removes, or reorders `use` statements, regenerate it with `make depend`
  (in a scratch rsync copy of `src/`, then strip trailing whitespace) and
  commit it in the same pull request. CI does not check it.

## Testing

Run the cheapest check that covers your change first.

- `pre-commit run --all-files`: seconds. Hooks are `trailing-whitespace`,
  `fortran-explicit-use` (`USE ... only` in `src/*.F`, some files excluded),
  `fortran-line-length` (132 characters in `.F90`), and `block-large-files`.
- `ci/compile_only.sh <build_dir> KEY [KEY...]`: one compile, no run. CI uses
  it for CPP-key combinations the pytest suite does not build.
- The pytest suite in `tests/`: slow, because it compiles ROMS per
  configuration, runs it under MPI, and hashes the NetCDF output against
  stored references. Inputs are generated by roms-tools; there is no download
  step. Run a subset with `-k` while iterating. Read `tests/README.md` first.

```bash
export ROMS_ROOT=/path/to/ucla-roms   # read at import; unset gives a KeyError
cd $ROMS_ROOT/tests
pytest -svvv -rfEx . --environ=github_gnu --tolerate-hash-mismatch
```

- Only `results_github_gnu.json` and `results_github_ifx.json` exist in
  `tests/results/`. A bare `pytest` uses `--environ=laptop`, which has no
  references, so every hashed test fails with "No reference results".
  `--tolerate-hash-mismatch` turns hash differences into XFAIL; compile errors
  and crashes still fail.
- Never hand-edit the reference JSON. To accept changed or new hashes, run
  `python tests/update_references.py --run <CI run id> --dry-run`, check that
  it lists exactly the keys you expect, then rerun without `--dry-run`.
- CI tests the pull request merged into current `main`, not the branch. If
  new tests fail only in CI, merge `main` into the branch and rerun.
- CI does not test a fork pull request's Containerfile changes: it runs the
  published `:latest` images. Make environment fixes for fork pull request CI
  in the workflow (`env:` or setup steps) instead.

## Repository layout

`src/` is the model (plus `Makedefs.inc`, the default `cppdefs.opt`, and
`namelist.nml`). `Tools-Roms/` holds `mpc`, `partit`, `ncjoin`, and other
tools. `tests/`, `ci/`, and `environments/` hold the pytest suite, workflow
helper scripts, and machine setup scripts plus CI container recipes. `docs/`
is the current documentation; `Documentation/` is unmaintained upstream notes,
so take no commands from it. `Examples/Iceland/` is the only tracked example.

## Namelist handling

`src/namelist.nml` is the canonical template. Each group header names its owning
module, for example `&RIVER_FRC_SETTINGS !river_frc.F90`.

- To add a key, declare the variable and add it to the `namelist /GROUP/`
  block in the owning module, then add a documented default to
  `src/namelist.nml`.
- A new group also needs its `read_nml_*` routine wired into `read_namelists`
  in `src/namelist_read_mod.F90`, respecting the CPP gates. Copy the pattern of
  `read_nml_river` in `src/river_frc.F90`.
- Array-valued keys, such as the per-child entries in `EXTRACT_DATA_SETTINGS`,
  take a scalar as element 1 only; `src/namelist.nml` says which have defaults.
- A nesting file's variable prefix must not contain `_`: ROMS uses the text
  before the first `_`.
- An older release stops on the new values, so C-Star needs a new namelist tier.

## Gotchas

- Never reference an optional argument in the same `.and.` expression as its
  `present()` test, as in `present(x) .and. x`. Fortran does not short-circuit
  `.and.`, and `PARALLEL_IO` builds at `BUILD_MODE=test` crash at startup on
  it. Nest the tests: `if (present(x)) then; if (x) ...`.
- Under `PARALLEL_IO`, every rank runs the collective write path, including
  ranks that hold none of an object's points. Per-rank work there needs a
  guard such as `np > 0`. ifx tolerates the unallocated arrays and gfortran
  segfaults. Without a gnu PIO stack, reproduce it with ifx and
  `USER_FFLAGS="-g -traceback -check pointers"`.
- Each CPP key set compiles a different subset of the source, so build and run
  every configuration your change touches.
- Scale: production runs use hundreds of MPI ranks across nodes, with every
  rank an I/O task. For an I/O or communication change, read the library's
  buffering, flush, and collective semantics in its source, and ask what the
  change does to memory and MPI traffic at that rank count. Run it at
  production size, or tell the user it is unverified at scale. Measure a
  performance change, and do not claim a gain you did not measure.

## Related repositories

roms-tools generates the NetCDF inputs ROMS reads. C-Star builds this
repository, writes the namelist, and runs the model. Forge, in C-Star under
`cstar/applications/forge`, templates `cppdefs.opt` and builds namelists.

- **Namelist.** A key or group change in `src/namelist.nml` needs a matching
  change in C-Star's namelist model (`cstar/roms/namelist.py`) and in Forge.
  Tick that item in the pull request template and say what must follow.
- **`cppdefs.opt`.** CPP keys select model features. Forge templates the file,
  and `Makedefs.inc` reads it to choose link dependencies.
- **Versions.** C-Star builds a chosen ucla-roms release, so a namelist change
  reaches users only through a new release plus a C-Star update.

## Data safety

Never delete or overwrite model output, restart files, scratch directories, or
another user's files without the user's explicit OK, even to start fresh.

## Release notes

`ci/update_release_notes.py` collects release notes from merged pull request
descriptions into `docs/releases/unreleased.rst` on the `next_release_notes`
branch. Write the Breaking Changes, New Features, Bug Fixes, Improvements, and
Miscellaneous sections of the description for users of the model. Do not edit
`docs/releases/` on a branch.

## Posting on GitHub

This project follows the [C]Worthy AI policy:
https://github.com/CWorthy-ocean/.github/blob/main/AI_POLICY.md

- You may draft pull request descriptions, bug reports, and summaries of test
  results for the user.
- Do not post replies, review comments, answers, or discussion comments on the
  user's behalf, and do not join a discussion on your own. If asked to, tell
  the user that the project asks for replies in their own words, and give them
  notes to write from. If they share your output, they quote it and say where
  it came from.
- Fill in `.github/PULL_REQUEST_TEMPLATE.md`, including the `AI disclosure:`
  line: `none`, or `<tool>; <what it did>`.
- Do not add `Co-authored-by`, `Assisted-by`, `Generated-by`, or similar AI
  trailers to commits.
- The user answers for what you open under their account. Tell them plainly
  what you did not run or could not verify.
